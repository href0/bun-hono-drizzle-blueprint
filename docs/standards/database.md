# Database & Drizzle — Implementation Guide

Read this file when: defining Drizzle tables, managing migrations with `drizzle-kit`, configuring PostgreSQL connection pooling, or auditing changes (`record_changes`).

---

## 1. Connection Pool (`src/database/connection.ts`)

Source of truth: `src/database/connection.ts` — read it rather than copying it. The essentials:

```typescript
import { databaseConfig } from '../config';

export const sqlClient = postgres(databaseConfig.DATABASE_URL, {
  max: databaseConfig.DB_MAX_CONNECTIONS, // DB_MAX_CONNECTIONS, default 20
  idle_timeout: databaseConfig.DB_IDLE_TIMEOUT_SECONDS, // default 30
  connect_timeout: 10,
});

export const db = drizzle(sqlClient, { schema });
```

- Settings come from the validated `databaseConfig` group (`src/config/database.config.ts`), never from `process.env`.
- The client is lazy: it connects on the first query, so importing it never opens a connection.
- Only `src/database/**` and `src/index.ts` (startup check, shutdown `sqlClient.end()`) may import it — modules use `TransactionHost` (§7). Health checks use `pingDatabase()` (`src/database/health-probe.ts`, 2 s timeout).
- Tests never reach a real database: `bunfig.toml` preloads `test/setup/hermetic-env.ts`, which points `DATABASE_URL` at a closed local port whatever the local env file says.

## 2. Tables (`src/database/schema/schemas.ts`)

A project owns its database (`<project>_db`, created by `init-project`), so its tables live in PostgreSQL's default `public` schema — nothing to configure or migrate per environment. Schema-per-tenant SaaS is a separate, optional feature ([decisions.md](../decisions.md) §3).

| Declared with | Contains | Migrated by drizzle-kit |
|---|---|---|
| `appTable(...)` (= `pgTable`, `public`) | Every table of this project | Yes (`schemaFilter: ['public']`) |
| `referenceSchema.view(...).existing()` | Optional: data owned by another system | Never |

- `schemas.ts` is the only file that calls `pgTable` / `pgSchema` (ESLint) — the single switch if the layout ever changes.
- `referenceSchema` is deliberately **not** re-exported from `src/database/schema/index.ts`: drizzle-kit emits `CREATE SCHEMA` for every exported `pgSchema` it finds there.

### Domain table (`src/database/schema/domain/<name>.schema.ts`)

```typescript
import { boolean, varchar } from 'drizzle-orm/pg-core';
import { timestamps, uuidPrimaryKey } from '../columns';
import { appTable } from '../schemas';

export const users = appTable('users', {
  id: uuidPrimaryKey(),
  email: varchar('email', { length: 255 }).notNull().unique(),
  isActive: boolean('is_active').notNull().default(true),
  ...timestamps(),
});
```

Re-export it from `src/database/schema/domain/index.ts`. In schema files ESLint rejects raw `timestamp(`, `date(`, `serial(`/`bigserial(`, `pgTable(` and `.defaultRandom()` — use the helpers below.

### Reference data (optional, `src/database/schema/reference/<name>.schema.ts`)

```typescript
export const refRoles = referenceSchema
  .view('ref_roles', {
    code: varchar('code', { length: 50 }).notNull(),
    name: varchar('name', { length: 100 }).notNull(),
  })
  .existing();
```

Selecting works; `db.insert(refRoles)` does not compile (guarded by a `@ts-expect-error` test). Delete the example if your project reads no external data.

## 3. Column helpers (`src/database/schema/columns.ts`)

| Helper | Column(s) | TypeScript value |
|---|---|---|
| `uuidPrimaryKey()` | `id uuid PRIMARY KEY` — UUID v7 generated by the app | `string` |
| `sequentialPrimaryKey()` | `id bigint GENERATED ALWAYS AS IDENTITY` — **only** tables in `APPEND_ONLY_TABLES` | `number` (mode `number`, safe to 2^53) |
| `sequentialId()` | the same identity without `PRIMARY KEY`, for a composite partition-ready key (`record_changes`) — same restriction | `number` |
| `timestamps()` | `created_at`, `updated_at timestamptz NOT NULL DEFAULT now()`; on update `BaseRepository` sets `updated_at = now()` (`$onUpdate` is only an application-clock fallback — drizzle binds its result as a parameter) | `Temporal.Instant` |
| `NOW` | `` sql`now()` `` — the database clock (transaction start) for every server-set time: defaults, `updatedAt: NOW` in updates, `record_changes.changed_at` | — |
| `instant(name)` | `timestamptz` | `Temporal.Instant` |
| `calendarDate(name)` | `date` | `Temporal.PlainDate` |
| `timeZoneColumn(name)` | `varchar(64)` IANA zone | `string` |
| `auditColumns()` | `created_by`, `updated_by varchar(150) NOT NULL` — filled by the base repository | `string` |
| `softDelete()` | `deleted_at timestamptz` | `Temporal.Instant \| null` |
| `parentReference(name, () => parent.id)` | `uuid NOT NULL` FK, `ON DELETE restrict` — add an index starting with it | `string` |
| `activeUniqueIndex(name, [cols], t.deletedAt)` | `UNIQUE INDEX … WHERE "deleted_at" is null` — use instead of `.unique()` on soft-deleted tables | — |

Time values follow [datetime.md](datetime.md): the driver hands `timestamptz`/`date` over as text, the helpers map them to Temporal with full microsecond precision.

### Choosing a primary key

- **Default: `uuidPrimaryKey()`** — UUID v7 is time-ordered (B-tree inserts stay at the right edge, like a sequence) and not guessable, so ids can appear in URLs. It is generated by the application (`Bun.randomUUIDv7()`; PostgreSQL 16 has no `uuidv7()`), so **raw SQL inserts must supply `id`**.
- **`sequentialPrimaryKey()`** only for high-volume, append-only records (audit trail, logs, history) that are never addressed by id in a public URL — sequential ids invite enumeration. Register the table in `src/database/schema/append-only-tables.ts` with the reason; the schema convention test (`src/database/schema/schema-conventions.test.ts`) rejects unlisted tables and stale entries.

---

### Schema conventions (checked on every exported table)

`src/database/schema/schema-conventions.test.ts` iterates every table exported from `src/database/schema/index.ts` (what drizzle-kit migrates) and fails with `<table>.<column>: <rule>`:

| Rule | Why |
|---|---|
| Every foreign key is the leading part of an index (an index, a unique column or the primary key) | PostgreSQL does not index FKs itself: joins and `ON DELETE` checks would scan |
| `id` comes from `uuidPrimaryKey()` — or `sequentialPrimaryKey()` / `sequentialId()` for tables in `APPEND_ONLY_TABLES` | One id strategy; sequential ids never become public resource ids |
| Every `APPEND_ONLY_TABLES` entry is an exported table with a sequential id | No stale allowlist entries |
| No `serial` / `bigserial` columns | Identity through the helpers instead |
| A table with `deleted_at` has no plain unique (column, constraint or index without `WHERE`), except a named `uniqueIndex` listed in `PERMANENT_UNIQUE_INDEXES` (`src/database/schema/permanent-unique-indexes.ts`) with its reason | A soft-deleted row would block re-creating the value — use `activeUniqueIndex()`. A value that must never be reused (e.g. a code that names an audit actor) is the deliberate exception |
| Every `PERMANENT_UNIQUE_INDEXES` entry names a plain unique index of a soft-deleted exported table | No stale allowlist entries |
| `record_changes`: primary key `(id, changed_at)`, no FK / unique, action and parent CHECKs | Partition-ready audit trail |

Each check is also proven against a deliberately broken table in the same file.

## 4. Migrations (`drizzle.config.ts`)

Source of truth: `drizzle.config.ts` (a standalone drizzle-kit config, allowed to read `process.env` — [configuration.md](configuration.md)). It generates migrations from `src/database/schema/index.ts` into `./drizzle`, limited to the `public` schema (`schemaFilter: ['public']`).

- Generate: `bun run db:generate` (offline — compares the schema files with the last snapshot). Apply: `bun run db:migrate` — **run by the developer** by default. An AI agent may run migrations and read-only checks only against the developer's **local** database, and only with the developer's explicit permission; destructive SQL or writing test rows is always asked first; never a shared or production database.
- `test/migrations.test.ts` guards the output: no `CREATE SCHEMA`, every table in `public`, ids without a database `gen_random_uuid()` default, the `record_changes` CHECK equal to `RECORD_CHANGE_ACTIONS`, `record_changes` keyed `(id, changed_at)` without foreign keys, `parent_table`/`parent_id` paired by a CHECK.

## 5. Audit trail (`record_changes`, `AuditedRepository`)

Every UPDATE, soft delete, restore and hard delete of an audited table appends one row to `record_changes` (`src/database/schema/domain/record-changes.schema.ts`), **in the same transaction** as the change: a rolled-back change leaves no audit row. INSERTs are not recorded — the row itself is the record (`created_at`, `created_by`).

| Column | Content |
|---|---|
| `id`, `changed_at` | `bigint` identity + `timestamptz` (transaction time); together the primary key, so the table can later be partitioned by month |
| `table_name`, `record_id` | Which row (lookup index `(table_name, record_id, changed_at DESC)`) |
| `action` | `UPDATE` · `SOFT_DELETE` · `RESTORE` · `DELETE` (CHECK) |
| `changes` | `jsonb` keyed by **column name**: `{ "full_name": { "from": "A", "to": "B" } }` for changed columns only; for `DELETE` the whole row. Redacted columns: `"[REDACTED]"` |
| `actor`, `request_id` | From the request context (`user:<id>`, `webhook:<vendor>`, `anonymous`, …; `system` outside a request) |
| `parent_table`, `parent_id` | The header of a detail row (`ChildRepository`) — both set or both null (CHECK). A header's full history, including its hard-deleted details: `where (table_name = 'orders' and record_id = $1) or (parent_table = 'orders' and parent_id = $1) order by changed_at` (partial index `record_changes_parent_idx`) |

No foreign keys and no other unique constraints: the audited row may be deleted, and a partitioned table needs the partition key in every unique index.

`src/database/audited.repository.ts` — abstract base with the primitives that `BaseRepository` / `ChildRepository` (§6) compose into update / soft delete / restore / delete. Modules extend those two; extend `AuditedRepository` directly only for an unusual write path, like this:

```typescript
class OrdersRepository extends AuditedRepository<typeof orders> {
  constructor(txHost: TransactionHost = defaultTxHost) {
    super(orders, txHost, { redact: ['secretNote'] }); // values never stored, changes still recorded
  }

  async rename(id: string, name: string): Promise<Order | null> {
    return this.inTransaction(async () => {          // own transaction, or join the caller's
      const before = await this.lockById(id);        // SELECT … FOR UPDATE
      if (!before) return null;
      const changes = this.diff(before, { name });   // {} when nothing changed (updated_at/updated_by ignored)
      if (Object.keys(changes).length === 0) return before;
      await this.txHost.tx.update(orders).set({ name }).where(eq(orders.id, id));
      await this.writeChange('UPDATE', id, changes); // empty change set writes nothing
      return { ...before, name };
    });
  }
}
```

- `writeChange(action, id, changes, { table: orders, id: orderId })` — the optional 4th argument records the header of a detail row.
- `lockById` and `writeChange` throw outside a transaction — use `inTransaction()` (`TransactionHost.run`).
- Values are compared and stored in JSON form: `Temporal` values as ISO strings; `jsonb` objects with the same members in another key order are not a change.
- Pure helpers: `diffRecords` / `snapshotRecord` in `src/utils/record-diff.util.ts`.
- Tests use the SQL recorder: the audit `insert` and the change appear between the same `BEGIN` and `COMMIT` / `ROLLBACK` (`src/database/audited.repository.test.ts`). Real rollback against PostgreSQL: `test/integration/data-layer.int.ts` ([testing.md](testing.md) §7).

## 6. Table kinds & repositories (`src/database/*.repository.ts`)

| Kind | Shape | Key columns | Repository |
|---|---|---|---|
| Standalone | Stands on its own | `uuidPrimaryKey` + `timestamps` + `auditColumns` + `softDelete` | `BaseRepository` |
| Header | Standalone with details | same | `BaseRepository` + a `ChildRepository` for its details (same module) |
| Detail | Only meaningful inside one header | `uuidPrimaryKey` + `parentReference` (indexed) + `timestamps` + `auditColumns`, **no** `softDelete` | `ChildRepository` |
| Dependent | Own page, always under one parent (standalone / header), added any time after it (D33); 1:N, or 1:1 with an `activeUniqueIndex` on the parent column | standalone shape + `parentReference` (indexed) | `DependentRepository` (own module, in a subfolder of the parent's) |
| Record | Log / history, append-only | `sequentialPrimaryKey` + `timestamps` (listed in `APPEND_ONLY_TABLES`) | `AppendOnlyRepository` |
| Reference | Owned by another system | view `.existing()` | `ReadOnlyRepository` |
| Refresh token (exception) | `auth_refresh_tokens` only | `uuidPrimaryKey` + `parentReference(user_id)` + own `created_at` / `revoked_at` | plain class in `auth.repository.ts` (see below); expired rows deleted by `src/database/maintenance/purge-refresh-tokens.ts` (`bun run auth:purge-tokens`) |

```typescript
export class OrdersRepository extends BaseRepository<typeof orders> {
  constructor(txHost: TransactionHost = defaultTxHost) {
    super(orders, txHost, { redact: ['internalNote'] });
  }
  // domain-specific reads: build them on this.scoped(...) so deleted rows stay hidden
}

export class OrderLinesRepository extends ChildRepository<typeof orderLines, typeof orders> {
  constructor(txHost: TransactionHost = defaultTxHost) {
    super(orderLines, orders, orderLines.orderId, txHost);
  }
}
```

**`BaseRepository`** — `findById`, `findPage({ page, perPage, orderBy?, where? })` (default `created_at DESC, id DESC`), `count(where?)`, `findList(query, columns, where?)`, `create`, `updateById`, `softDeleteById`, `restoreById`:
- Reads see live rows only (`scoped()` = `deleted_at IS NULL` + your conditions); there is no hard delete.
- `create` stamps `created_by` / `updated_by` with the request actor. Managed columns (`createdAt`, `createdBy`, `updatedAt`, `updatedBy`, `deletedAt`; `id` on update) are dropped from caller input, even when a DTO spread smuggles them in.
- `updateById` locks the row, diffs, and writes only when something changed: `updated_at = now()` (database clock, set explicitly — drizzle binds `$onUpdate` results as parameters), `updated_by = actor`, plus the `record_changes` row. `null` = missing or soft-deleted; the unchanged row = nothing to write.
- `softDeleteById` / `restoreById` set or clear `deleted_at` and audit `SOFT_DELETE` / `RESTORE`. A restore can hit an `activeUniqueIndex` conflict (a live row took the value meanwhile) — the service maps it to a `ConflictError`.

**`ChildRepository`** — every method takes the header id first: `findAllForParent`, `findByIdForParent`, `createForParent`, `updateForParent`, `deleteForParent`, `syncForParent`:
- A detail is reachable only through its own header: an id of another header's detail is `null` / `false` (no IDOR). A missing or soft-deleted header is `NotFoundError`.
- Writes lock the live header first, then its details ordered by id — one lock order for every writer, so concurrent edits of one header queue instead of deadlocking. The detail's header reference cannot be changed through input.
- Every detail change is audited with `parent_table` / `parent_id`, deletes are hard deletes with a snapshot, and the header's `updated_at` / `updated_by` are touched when something changed.
- `syncForParent(headerId, items)` saves a form's complete list in one transaction: items with `id` are updated (when changed), items without are inserted, details missing from the list are deleted. An unknown `id` is `NotFoundError`, a repeated one `BadRequestError`.
- `protected assertParentWritable(header)` is called with the locked header before every write (default: always writable); override it to refuse changes by the header's state (e.g. a submitted order → `ConflictError`).

**`DependentRepository`** — a row with its own page and soft delete that always belongs to one parent: `findById`, `findPageForParent`, `countForParent`, `findListForParent`, `createForParent`, `updateById`, `softDeleteById`, `restoreById`, and for 1:1 tables `findOneForParent`, `upsertForParent`, `softDeleteForParent`:
- Reads see a row only while it is live **and** its parent is live and inside `parentScope()` (an `EXISTS` on the parent). Deleting the parent hides its rows without touching them (no cascade); restoring the parent brings back the rows that were live — a row deleted on its own stays deleted. Restoring a row while its parent is deleted is `null` (404).
- Writes lock the visible parent first (`FOR SHARE`; `FOR UPDATE` for `upsertForParent`, so concurrent saves of one parent queue), then the row (`FOR UPDATE`), and call `assertParentWritable(parent)`. The parent reference never changes through input. Updates, soft deletes and restores are audited with the parent in `parent_table` / `parent_id`; creating is not (the row is the record).
- **Ownership**: override `protected parentScope(): SQL | undefined` (e.g. `eq(projects.ownerId, …)`) and every read and write of the rows is limited to parents in scope. A parent that is missing, deleted or out of scope is `NotFoundError` for parent-scoped calls and `null` for calls by id — a 404 either way, so another owner's data is never confirmed to exist. The parent module's own list and detail still need their own owner filter.
- 1:1: the `activeUniqueIndex` on the parent column counts live rows only — after a soft delete a new row may be created; restoring the old one while a live one exists is a unique violation (the service maps it to `ConflictError`).
- At most two levels: the parent is a standalone or header table, never a dependent one (`bun run scaffold` refuses it).

**`AppendOnlyRepository`** — `append`, `findPage({ page, perPage, where?, orderBy? })` (default `id DESC`), `count(where?)`, `findList(query, columns, where?)`. No update, no delete, nothing audited: the table is the record. Retention is an operational job (partitions), not application code.

**`ReadOnlyRepository`** — `findPage({ page, perPage, where?, orderBy })` (order required: a view has no key) and `count(where?)` over a `.existing()` view. Writes are impossible twice over: no write method, and Drizzle rejects `insert` / `update` / `delete` on a view at compile time.

Every module repository extends one of these five and module code never writes around them — rules in §7.

**List queries** (`http-contract.md` §8): a module repository declares its allowlist once — `const <NAME>_LIST_COLUMNS: ListColumns<<Name>SortField> = { sort: { createdAt: table.createdAt, … }, search: [table.name] }` (a sortable DTO field without a column does not compile) — and one method, e.g. `findUserList(query)`, that passes the module's typed filters as `where` to `findList` / `findListForParent`. `findList` reads the page and the total side by side under the same conditions (live-row and parent scope always included), orders by the sort keys and then `id` (`orderFromSort`), and adds `q` as an OR of `ILIKE` over the search columns (`searchCondition`, `escapeLike`); helpers in `src/database/list-query.ts`, e.g. `instantRange(column, from, to)`. SQL stays in the repository: services pass the DTO through.

Reference implementations: `src/modules/orders/` (header + detail, generated from the scaffold header-detail template), `src/modules/projects/` with its dependents `project-tasks/` (1:N) and `project-budgets/` (1:1) (generated with `--parent`; both examples removed by `bun run setup <name>` unless `--keep-examples`) and `src/modules/users/` — `UsersRepository extends BaseRepository` (redacts `passwordHash`), the service maps `null` to `NotFoundError` and a unique violation (`isUniqueViolation()` from `src/database`, SQLSTATE 23505) to `ConflictError` on create, update and restore, and evicts the cached detail after every write.

Generic behaviour is tested once, with the SQL recorder and test-only tables (`test/helpers/repository-fixtures.ts`): `src/database/{base,child,dependent,append-only,read-only}.repository.test.ts`, and against a real PostgreSQL in `test/integration/data-layer.int.ts`. Module repositories test only what they add.

## 7. Machine-enforced data-layer rules

Every change of a domain row goes through a base repository (row lock, soft-delete scope, actor stamps, `record_changes` in the same transaction). These rules make every shortcut fail lint:

| Rule | Applies to | Enforcer |
|---|---|---|
| A repository class `extends` `BaseRepository` / `ChildRepository` / `DependentRepository` / `AppendOnlyRepository` / `ReadOnlyRepository` | `src/modules/**/*.repository.ts` | [eslint:REPOSITORY_SYNTAX_RULES] |
| No `tx.update(` / `tx.delete(` (use `updateById`, `softDeleteById`, `ChildRepository`, …) | module repositories | [eslint:REPOSITORY_SYNTAX_RULES] |
| No `tx.insert(` / `tx.update(` / `tx.delete(` | module files other than repositories | [eslint:TX_WRITE_RULES] |
| No `UPDATE` / `DELETE FROM` inside `` sql`…` `` | every module file | [eslint:RAW_WRITE_SQL_RULES] |
| `tx.execute(` (raw query) only in `<name>.queries.ts` (pure, read-only functions — [raw-queries.md](raw-queries.md)) | modules | [eslint:RAW_QUERY_RULES] |
| The transaction is used as `this.txHost.tx`, never kept in a variable or destructured (the write rules recognize it by name) | modules | [eslint:TX_ALIAS_RULES] |
| `@Transactional()` only in `*.service.ts` | modules | [eslint:TRANSACTIONAL_RULES] |
| `TransactionHost` / `defaultTxHost` / `transactionStorage` only in repositories and `*.queries.ts` (module tests may use them) | modules | [eslint:TX_HOST_IMPORT_PATTERN] [depcruise:transaction-host-only-in-repositories] |
| `db`, `sqlClient`, `database/connection` never imported | modules | [eslint:MODULE_SYNTAX_RULES] [eslint:MODULE_IMPORT_PATTERNS] [depcruise:no-module-direct-db-connection] |
| `recordChanges` not imported outside `src/database/` (also through the barrel) | all of `src/` | [eslint:MODULE_IMPORT_PATTERNS] [depcruise:record-changes-only-in-database] |
| No `sql.raw(` (use `sql.identifier()`; a static fragment = `eslint-disable` + reason) | all of `src/` | [eslint:SQL_RAW_RULES] |

- **The one approved exception** ([decisions.md](../decisions.md) §2): the refresh-token repository `src/modules/auth/auth.repository.ts` (table `auth_refresh_tokens`: high-volume security state without audit columns or soft delete — `revoked_at` + `replaced_by_id` are its trail). A one-file override in `eslint.config.mjs` (`AUTH_TOKEN_REPOSITORY_RULES`) lets it skip the base and `tx.update(authRefreshTokens)` only; updating any other table and `tx.delete` stay rejected.
- **Seeders** (`src/database/seeds/**`) belong to the database layer, not to a module: the module rules do not apply, but they still write through the base repositories (actor `system`, audited). Example: `seed-admin.ts` (password from a masked prompt / stdin, never argv or env).
- `users.role` is matched against `ROLES` (`src/core/security/roles.ts`) by `src/database/roles-column.test.ts`.
- `[review-only]`: custom reads inside a `BaseRepository` subclass start from `this.scoped(...)` so deleted rows stay hidden.
