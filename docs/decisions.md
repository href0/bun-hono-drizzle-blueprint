# Decisions

Why this boilerplate is built the way it is. An ID such as `D13` in a comment, a test or a document points to a row below; the rule each decision produced is in `ARCHITECTURE.md` §12 and its standard in `docs/standards/`. The boilerplate was adopted from a NestJS + Drizzle blueprint, which is not part of this repository.

A changed decision keeps its ID: the row says what replaced what. **Numbering**: `D…` belongs to the boilerplate (§1). A project created from it records its own decisions as `PD1`, `PD2`, … in §4, so a later boilerplate decision taken over from `upstream` never collides with one of the project's. How a work plan feeds this file: [docs/plans/README.md](plans/README.md).

## 1. Decisions

| ID | Decision | Why |
|---|---|---|
| D0 | The boilerplate repository works on `main` with one branch per change; `development → staging → prod` is for projects created from it ([git-workflow.md](standards/git-workflow.md)) | A template has no environments of its own |
| D1 | Refresh tokens are opaque, stored as a SHA-256 hash in `auth_refresh_tokens`, rotated on every refresh; reuse of a rotated token revokes its whole family | A stateless JWT refresh cannot be revoked; Redis fails open, so session state cannot live there |
| D2 | Access tokens: JWT HS256 (`hono/jwt`), 15 minutes, claims `sub`, `role`, `jti`, `iss`, `aud` | No extra dependency; JWKS / asymmetric keys stay in the backlog |
| D3 | The refresh token travels only in the `refresh_token` cookie: `HttpOnly; Secure; SameSite=Strict; Path=<base>/v1/auth`, `Max-Age` = its TTL; never in a body | Unreachable from scripts; `Secure` still works on `http://localhost` |
| D4 | Cookie endpoints are protected by `SameSite` plus an `Origin` / `Sec-Fetch-Site` check against `CORS_ORIGINS` | The frontend manages no CSRF token |
| D5 | Login is email + password (argon2id via `Bun.password`); public registration is off (`AUTH_REGISTRATION_ENABLED=false`) | Admins create users |
| D6 | Authorization is simple RBAC: `users.role` ∈ `ROLES` + `requireRole()` — **superseded** by permission-based RBAC (D46–D61, D64–D71) | Fine-grained permissions stay in the backlog |
| D7 | Routes are default-deny: `authenticate()` on every `/v1` route except `PUBLIC_ROUTES`, proven by enumerating `app.routes` | A forgotten guard must not open a route |
| D8 | Request context (request ID, actor, locale, client IP) lives in `AsyncLocalStorage` | Services never receive the Hono `Context` |
| D9 | `X-Request-ID` is accepted only when it matches `^[A-Za-z0-9._:-]{1,128}$`, otherwise a UUID v7 is generated | Prevents log injection |
| D10 | The wire is snake_case in both directions and strict: another key casing in a request is a 400; opt-out `preserveKeys` | A symmetric contract; error `field`s match what the client sent |
| D11 | Messages in `id` and `en`, chosen by `Accept-Language`, default `DEFAULT_LOCALE=id` | Localized messages are one of the platform pillars kept from the blueprint, instead of shrinking to English only |
| D12 | A unique-value collision is `ConflictError` (409, `CONFLICT`) | The standard status for a general-purpose API |
| D13 | Time uses `temporal-polyfill`; runtime and database sessions run in UTC; three kinds of time: instants, calendar dates, local schedules with a zone ([datetime.md](standards/datetime.md)) | Prevents time-zone bugs |
| D14 | Tables live in `public` through `appTable`; reference data owned by another system is a `.view().existing()` (replaced: one `pgSchema` named after the project) | Each project owns its database |
| D15 | Primary keys are UUID v7 made by the application; a sequential `bigint` identity only for high-volume record tables listed in `APPEND_ONLY_TABLES`, never as a public id | B-tree indexes stay compact; ids cannot be enumerated |
| D16 | `record_changes`: one generic, partition-ready audit table written by the base repositories in the same transaction | No update or delete can skip its trail |
| D17 | OpenAPI through `hono-openapi` + Scalar, generated from the route code | One source; documents cannot drift |
| D18 | Rate limits in Redis (atomic `increment`, fixed window, fail-open, keyed by the trusted client IP) | Holds across instances |
| D19 | Quality gates: knip instead of depcheck; coverage without test files — global lines and functions ≥ 95 %, per file ≥ 90 %; pre-push runs the whole gate; CI on GitHub Actions | Bun reports no branch coverage |
| D20 | Dependency injection by singleton + default constructor parameter | Simple, easy to replace in tests |
| D21 | Partner API under its own prefix `/api/v1/partner/*` with `partnerAuth()` and the `partner-credentials` module | Never mixed with the JWT routes |
| D22 | Redis reconnects forever (backoff ≤ 30 s), no offline queue, a command timeout, the key prefix `<APP_NAME>:<NODE_ENV>:`, `FLUSHALL` / `FLUSHDB` / `KEYS` refused | Resilient and safe on a shared server |
| D23 | Two inbound channels: the partner API `<base>/v1/partner/*` (our contract, `partnerAuth()`) and vendor webhooks `<base>/webhooks/<vendor>` (the vendor's contract, outside `/v1`, one verifier per vendor, fail-closed) | Vendors never follow our signing; loosening `partnerAuth()` would weaken every partner |
| D24 | Module file names: `<module>[.<channel>].<role>[.test].ts`, channel `partner` / `webhook`, the role last | Lint and dependency rules read the suffix; `x.partner-routes.ts` would escape them all |
| D25 | Vendor adapters: `src/integrations/<vendor>/<vendor>.<role>.ts` (`service`, `dto`, `webhook`, `webhook.dto`, `index.ts`) | Everything about one vendor in one place |
| D26 | Modules are named after their domain, never after a vendor | Changing vendors adds an adapter; the module stays |
| D27 | An endpoint for one partner also checks `requirePartner(...codes)` in code, besides `allowed_routes` | A misconfigured `allowed_routes` cannot open it to another partner |
| D28 | Inbound idempotency is mandatory: `webhook_events` unique (vendor, event id); partner writes unique (`partner_code`, `partner_reference`) | Nonces and a fail-open Redis do not guarantee "processed once" |
| D29 | The partner and webhook prefixes are outside the global per-IP limit; per IP only refused attempts (401 / 403) are counted (`rejectionLimit()`) | The global limit would silently cap a partner's quota and refuse vendor retries |
| D30 | `bun run setup` removes the example webhook (`demo-pay` + `payment-notifications`) like the other examples; the partner ping / echo stays | New projects start without a fictitious vendor; ping / echo serves partner onboarding |
| D31 | A CLI scaffolder `bun run scaffold <kind> <name>` generates from the `scaffold-module` templates (the Markdown stays the single source), verified by `verify:scaffold` | Conventions hold without an AI agent |
| D32 | Every standard lives once, in `docs/standards/<topic>.md`; `ARCHITECTURE.md` is the why and the rule index; `CONTRIBUTING.md`, `AGENTS.md` and the skills only route | Standards written four times in two languages always drifted |
| D33 | Dependent modules: a child with its own pages under a parent (`--parent`, `--one` for 1:1), in the parent's subfolder, shallow routes, `DependentRepository` (a deleted parent hides its children, no cascade; `parentScope()` / `assertParentWritable()` hooks) | Parent rules are enforced once, in the base repository |
| D34 | API contract snapshot `docs/api/openapi.json`: `openapi:check` (pre-push, CI) fails on any change with `BREAKING` / safe / docs labels; only a developer runs `openapi:update` | Contract changes become visible and reviewed |
| D35 | `docs/api/*.md` is generated from the same document: one file per module, every status with its codes, examples; `describeEndpoint()` declares error codes and the success message, checked at run time under `NODE_ENV=test` | Hand-written docs drift; integrators need the codes |
| D36 | `bun run scaffold` asks what is missing in a terminal (a wizard over the same flags, `@clack/prompts`) and prints the equivalent command; without a terminal it never asks | Flags are easy to forget; the printed command teaches them |
| D37 | `bun run acceptance` runs the whole path of a new developer without any input: per setup combination a fresh clone, setup, every generator (the wizards answered by the runner), gates, database, server, HTTP, Docker | One command, repeated before every release |
| D38 | `bun run setup` takes arguments or a wizard, no configuration file; `--title`; the outbound example is removed like the others; `--no-partner` prunes the partner gateway | A project's identity is only its name, title and description |
| D39 | The partner gateway is pruned by marked regions (`// partner:start` … `// partner:end`) plus `PARTNER_ONLY`; re-enabling it is manual for now | Markers are visible in the files and safe for documents |
| D40 | One `Prompter` for every CLI question; `bun run help` only prints the command registry; every script answers `--help` without side effects | Three prompt styles, and `--help` that ran the command |
| D41 | Every paginated list takes `sort` (allowlisted fields, ≤ 3, ended by `id`), `q` (`ILIKE` over declared columns) and typed filters; any other parameter is a 400 ([http-contract.md](standards/http-contract.md) §8) | Without one convention every project builds its own; the allowlist keeps sorting and filtering on known columns |
| D42 | The documentation portal stays on Astro Starlight, customized through `customCss` and component overrides rather than moved to VitePress or Docusaurus ([documentation.md](standards/documentation.md) §1) | `sync-docs.ts`, the sidebar check, the link check and the deploy workflow are built on it; Astro's own documentation uses it |
| D43 | The portal's content column grows with the screen (56 / 64 / 72rem from 72 / 90 / 120rem) instead of Starlight's fixed 45rem, code in a table cell may break anywhere, code blocks may still scroll | With 45rem the wide tables of the standards scrolled sideways even on a 1920px screen; measured on all 40 pages: tables that scroll 7–12 → 0 on desktop, 183 → 19 on a phone |
| D44 | The portal's fonts are self-hosted (`@fontsource`), its accent palette passes WCAG AA for every text pair in both themes | No request to a third party, works offline and on a closed network; readable for everyone |
| D45 | The portal shows facts read from their source: the version from `package.json`, each page's date from its source's last commit, "Edit page" to the source file (never the generated API contract) | One source each; a project created from the boilerplate shows its own version without edits, and nobody edits a synced copy or a generated file |
| D46 | RBAC is mandatory in every project; there is no "signed in without a role" mode | Forgotten access is broken access control; one code path; almost free for a simple app (the super admin role comes from `setup`) |
| D47 | A permission is an **action** (`orders.read`, `.create`, `.update`, `.delete`, `.restore`) that may cover several endpoints; the list of endpoints per permission is derived from the routes, its description from OpenAPI | More stable than one per endpoint (paths change, grants stay); an administrator ticks one box per intent |
| D48 | Permissions live in the **database**: API permissions come from a registry in code and are synced; **menu** permissions are created by administrators; the frontend reads `GET /me/permissions` | Administrators manage access and menus; an API permission no route checks would mean nothing |
| D49 | Every route names its permission (`requirePermission`) or states it is open to every signed-in user (`allowAnyUser()`) — a test fails otherwise (R89); the app refuses to start while a permission of the code is missing from the database | RBAC cannot be forgotten — the default-deny of D7 extended to authorization |
| D50 | A user may hold **several roles** | Fewer per-user grants |
| D51 | Per-user grants only **add** (none at first), with an optional `expires_at` and a note; no per-user denial | Simple and auditable; "everyone but A" is a separate role |
| D52 | Effective permissions = the permissions of every live role ∪ live, unexpired grants; `super_admin` holds every permission and cannot be changed (anti-lockout) | Roles as the base layer, users as additions |
| D53 | Permissions are **not** in the JWT: read per request through a per-user cache (one key function), dropped on every change; every change is in the audit trail | A 15-minute token would delay every change of access |
| D54 | `bun run scaffold` generates a module's CRUD permissions (`<module>.permissions.ts`, a constant per action); `bun run setup` / `seed:admin` give the super admin role | The permission list stays complete without writing it by hand |
| D55 | `user_roles (id, user_id, role_id, audit)` and `user_permissions (id, user_id, permission_id, expires_at, note, audit)` have their own UUID v7 `id` (no composite key); soft delete = revocation; unique among live rows only | Adding `tenant_id` later changes no primary key, foreign key or API |
| D56 | Ready for tenants without a `tenant_id` today: every RBAC query goes through one filter (`rbacScope()`), cache keys come from one function, no endpoint takes a tenant from the client. When tenancy comes: `user_roles` / `user_permissions` get `tenant_id NOT NULL` (their live-row uniques include it), `roles` gets `tenant_id` (NULL = system role), `permissions` / `role_permissions` stay global | A dead column misleads and `NULL` in a unique traps; one later migration is enough |
| D57 | "Every route names its permission" applies to routes with a user's JWT; `PUBLIC_ROUTES`, the partner gateway and webhook receivers have guards of their own and are excluded explicitly — still each route in exactly one category (R89) | Partners and vendors are not users; a permission there would mean nothing |
| D58 | The role leaves the JWT and `users.role` is dropped: `0010_rbac.sql` moves `admin` → `super_admin`, `user` → `user` (`user_roles`), `0011_drop_users_role.sql` drops the column (v1.x was never published, so one release, not two); `requireRole` / `requireSelfOrRole` / `ROLES` / `DEFAULT_ROLE` are removed; an old token carrying `role` is accepted, the claim ignored | Several roles (D50) do not fit one claim; a role in the token delays a revocation like D53 |
| D59 | `user` is a system role (mappable, never deleted) given to every new user — sign-up or created without a role — with no permission at first (only `allowAnyUser()` routes) | Sign-up keeps working; the app stays safe before an administrator configures anything |
| D60 | A registry permission may have actions beyond the five CRUD ones (`partner-credentials.rotate-secret`); scaffold generates only the five | Modules with actions of their own |
| D61 | Released as a **MAJOR** version (`v2.0.0`) with an upgrade guide for derived projects (`CHANGELOG.md` → *Upgrading a project*); the breaking changes stay under `/v1` (no `/v2` router, R19 exception) because no client used v1.x | The core public API changes; derived projects must change code |
| D62 | Every local command names its environment: `bun run start:<dev\|test\|stg\|demo\|prod>` (`bun --env-file` straight to the server; `start:dev` / `start:test` pipe its output through a SIGINT-ignoring `cat`, so a Bun process exiting after `bun run` cannot reset the terminal) and `bun run env <environment> <command>` (`scripts/with-env.ts`) load `.env.<environment>` only; `.env` and `bun run dev` are gone, the launcher and the app refuse while a file Bun loads by itself exists, and drizzle-kit has no default database. Containers and servers inject their variables and run `bun run start` / `db:migrate` directly. AI agents use dev and test only. | Bun loads `.env` / `.env.local` into every process — also a script's child — so a command silently hit whatever database that file named (one `db:migrate` reached the development database while its variable was unset); a named environment makes the target visible and lets the agent guard refuse staging, demo and production |
| D63 | Cache entries are dropped only after the change committed: `afterCommit(fn)` on the transaction host runs `fn` after the outermost commit (at once without a transaction, never after a rollback; a failure is logged, not thrown); every module invalidation goes through it, enforced by R88. Tests of services use `runInFakeTransaction` | A drop inside an open transaction let a concurrent read cache the old row again until the TTL (found in `users.updateUser` during plan RBAC step 3; `RbacService` dropped after its own transaction but not after a caller's). One mechanism closes the gap everywhere instead of per service |
| D64 | `permissions.source`: `api` rows are created and kept in step by the registry sync and never changed through the API (409); `menu` rows are created by administrators, keys prefixed `menu.` (CHECK) | Code owns what routes check; administrators own what frontends show |
| D65 | `role_permissions` has its own `id` and soft delete like `user_roles` | Every mapping change is audited in `record_changes` per row; unmapping is recorded |
| D66 | Every RBAC foreign key is `ON DELETE RESTRICT`; `user_id` and `role_id` are indexed | Soft delete everywhere, so an accidental hard delete is refused; lookups by user and invalidation by role stay fast |
| D67 | An API permission that left the registry is not deleted: the sync sets `retired_at` (it no longer counts), a key that returns is cleared | Mappings and grants survive a rename in two releases; history stays readable |
| D68 | The RBAC admin API lives in the `rbac` module, one route file per resource: `/roles`, `/permissions`, `/users/:id/roles`, `/users/:id/permissions`, `GET /me/permissions`; `PUT` of a mapping, assignment or grant is idempotent (201 / 200); the endpoints of each permission are read from the app's OpenAPI document (`x-allowed-callers`), built once per app and handed to the module through `permissionContext()` | One module owns the RBAC tables and their cache; the endpoint list cannot drift from the guards and works with `/docs` switched off |
| D69 | **No escalation**: whoever maps a permission, gives a role or a grant, restores a role, or changes another user's account (email, password, active flag, delete, restore) must hold every permission involved — 403 `ERR_PERMISSION_ESCALATION_FORBIDDEN`; `super_admin` is given and taken only by a super admin, never from oneself (403 `ERR_SELF_LOCKOUT_FORBIDDEN`) and never from the last live, active holder (409, holders locked `FOR UPDATE`, one rule in `src/database/rbac/super-admins.ts`); seeds and jobs (no signed-in user) are not checked; restoring a **menu** permission needs no such check — it steers a frontend menu and opens no endpoint | Without it a holder of `user-roles.create` or `users.update` (a password reset) could take any permission, and an administrator could lock everyone out |
| D70 | `openapi:check` labels a new code in the shared `error.code` enum of error responses `safe` | The set of codes is open — a client treats an unknown code as a generic error of its status; otherwise one new code flagged every error response as `BREAKING` |
| D71 | A plan with more than one step ends with a closing review of every step against the code, and the agent places review checkpoints during it (`docs/plans/README.md` → *Review checkpoints*) | Gates prove one step; gaps between steps (stale documents, a core test depending on an example module, another path to the same permission) show only when steps are read together |

## 2. Approved exceptions

- **Refresh-token repository** (`src/modules/auth/auth.repository.ts`, table `auth_refresh_tokens`): it does not extend a repository base and may `UPDATE` that one table directly (revoke, rotate) — high-volume security state without audit columns or soft delete; `revoked_at` + `replaced_by_id` are its trail. `DELETE` is not part of the exception: expired tokens are purged by `bun run auth:purge-tokens`. Enforced by the ESLint group `AUTH_TOKEN_REPOSITORY_RULES` ([database.md](standards/database.md) §7).

## 3. Backlog

Deliberately left out, to add when a project needs it:

- JWT with RS256 / EdDSA and a JWKS endpoint (verification across services); MFA, password reset and email verification by mail.
- Outbound retries with backoff and a circuit breaker; a vendor token cache shared across instances (Redis + lock) for vendors that allow one live token.
- A per-user rate limit after login; a list of sessions per device with revocation.
- Monthly partitions of `record_changes` with a retention runbook; OpenTelemetry tracing and `/metrics`; a job queue / scheduler with the actor `system`; outgoing webhooks (signing, retries, dead letters) and asynchronous processing of incoming ones.
- Re-encrypting partner secrets with a new active key without rotating them; requiring an `ip_whitelist` for partners in production; the partner gateway in an external API gateway.
- Zod 4; a header-detail with several details; dependent chains deeper than two levels; automatic document numbering.
- Large lists: cursor / keyset pagination, full-text search or `pg_trgm` indexes for `q`, lists across parents for dependents.
- Documentation portal: versions per release tag; Starlight's interface labels ("Last updated", "On this page") in Indonesian like the guides; the partner card on the home page (MDX has no partner markers, `project-setup.md` §4.2).
- `bun run feature:enable <feature>` — one command for every feature `bun run setup` can prune (first `partner`, later `tenancy`), taken from `upstream` at the release the project started from, like the NestJS template's — and the template sync command for projects created from the boilerplate on the same machinery (name to decide: `template:upgrade` follows this repository's `<area>:<action>`, the NestJS template uses `upgrade:template`). Its plan adds the acceptance combination `setup --no-partner`, then `feature:enable partner` (the restored gateway passes the gates and answers over HTTP).
- Multi-tenancy for SaaS, as an optional feature with its own plan — direction chosen 2026-10-31: one set of tables with `tenant_id` (not a schema per tenant: one migration run, scales to many tenants), and no data may cross tenants, guarded in layers: PostgreSQL row-level security on every tenant table, fail-closed when no tenant is set, the application connecting as a role that does not own the tables (migrations use another); base repositories scope and fill `tenant_id` from the request context, never from a DTO; the tenant comes from the JWT and the user's membership; unique keys and foreign keys include `tenant_id`; cache keys and background jobs carry the tenant; a convention test (every non-global table has `tenant_id` + a policy) and a two-tenant integration test, proven by chaos. Roles become per tenant — the RBAC tables are designed so a `tenant_id` can be added without changing their API. Chosen at `bun run setup`, not on by default: the wizard asks whether the project will serve more than one customer organisation (yes, or maybe later → on now, even with one tenant; internal → off), and says why in a sentence or two when it asks: on from the start costs one column per table, while switching later means checking every project table, every query outside the base repositories, cache keys, jobs and the production data. A project that switches later runs `bun run feature:enable tenancy`, which writes the backfill migration (a first tenant owning every existing row, `ADD COLUMN … NOT NULL DEFAULT <first tenant>` then `DROP DEFAULT`, memberships for existing users, policies) — `drizzle-kit generate` alone would emit a `NOT NULL` column that fails on a table with rows. Its plan adds acceptance combinations with and without tenancy, and classifies the new setup option (R91).
- A lite preset for plain CRUD applications, with its own plan after multi-tenancy — direction chosen 2026-11-06: one repository, `bun run setup --preset lite` (a preset is a set of pruned features on the D39 prune machinery, not a separate template). Lite keeps the layers, the HTTP contract, auth, RBAC, audit, cache and every quality gate, and every `module` variant of `bun run scaffold` (standalone, record, header-detail, dependent `--parent` / `--one`) — they are CRUD shapes and cost little to keep. It prunes the outside-boundary features with what supports them: `partner`, `webhook` and `integration` (their scaffold kinds, middlewares, modules, examples and HTTP client); a lite project gets one back with `bun run feature:enable <feature>`. Its plan adds the acceptance combinations `setup --preset lite` and lite then `feature:enable webhook`, and classifies `--preset lite` (R91).
- A gate that type-checks the tree `bun run setup --no-partner` leaves (the `PARTNER_ONLY` paths gone, every marked region pruned) — code valid in the boilerplate can break once a partner type is pruned (2026-11-07: `variant !== 'partner'` in the scaffold planner, TS2367), and today only `bun run acceptance` catches it. Measured ≈7 s; placement left open (a CI-only `verify:setup`, `lint:setup` or a test).
- Tenancy (plan of its own): restoring a role goes through the base repository (`restoreById`), which does not apply `rbacScope()` — once roles carry `tenant_id`, the restore must filter by tenant like every other RBAC query (found by the RBAC closing review, 2026-11-07).
- Migrations with only `DATABASE_URL`: `bun run db:migrate` syncs the permission registry through modules that import the configuration barrel, which builds every group at import — so the tools image needs the whole production environment (JWT, partner keys, Redis), as `docs/deployment.md` §3 gives it and CI now mirrors. Building config groups on first use (validated once at server start) plus a test that runs the sync with `DATABASE_URL` alone would give the migration job only the secrets it uses (found by the CI job `docker`, 2026-11-07).
- RBAC from the other side (chosen 2026-11-08: backlog only): today a role lists its permissions and a user its roles and grants. The reverse reads — the roles holding a permission, the users holding a role (paginated: users can be many), the users granted a permission — help audits ("who can delete orders?"). A reverse bulk write (one role to many users) only when a screen needs it, and then as a delta `{ add, remove }`, not a replace: a replace over many users revokes everyone the frontend left out.
- RBAC playground, its own plan after the bulk checklist endpoints (chosen 2026-11-08): one static page served by the app itself (e.g. `/dev/rbac`) that signs in and calls the real API — the permission catalog, the checklist of a role or a user, save — so it shows the actual rules and doubles as a frontend example. Served **only** when the app runs from the dev environment (`bun run start:dev`, `.env.dev`), never in test, stg, demo or prod; the app knows only `NODE_ENV` today, so the plan picks how it learns its environment (the launcher passing the name, or an opt-in variable off by default) and a test proves the route is absent elsewhere. Not in the documentation portal: it is static, and a copy of the rules in the browser (or SQLite / PGlite, while the schema is PostgreSQL) would drift from the backend.

## 4. Project decisions

A project created from this boilerplate adds its own decisions here (`PD1`, `PD2`, …), one row each, in the same form as §1. The boilerplate itself leaves this section empty.
